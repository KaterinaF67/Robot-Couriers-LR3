# Многоагентная система роботов-курьеров · ЛР3

Лабораторная работа № 3 «Проектирование механизма переговоров и разрешения конфликтов».

**Задача:** исследовать конкуренцию роботов за ограниченные зарядные станции. Сравниваются два правила выбора заявки: **FIFO** (по порядку поступления) и **приоритет** с учётом заряда и времени ожидания. В проведённых экспериментах приоритетное правило сокращало среднее ожидание срочных заявок при высокой нагрузке, но увеличивало максимальное ожидание.

Проект продолжает систему из ЛР2: склад с препятствиями, доставка заказов, автономные роботы, станции, сообщения и централизованное назначение / Contract Net.

## Что где лежит

- `mas/core.py` — модели роботов, станций, среды, сообщений и оба правила обслуживания зарядки.
- `run_lr3.py` — ручной запуск и сравнение механизмов ЛР3.
- `experiments_lr3.py` — 60 запусков (30 пар FIFO/приоритет) с одинаковыми начальными условиями.
- `plots_lr3.py` — построение графиков по CSV.
- `tests/` — 36 автоматических тестов, включая регрессионные проверки ЛР2 и новые проверки ЛР3.
- `results_lr3/` — CSV, конфигурация экспериментов и графики.
- `tools/stress_lr3.py` — дополнительная проверка на 100 сценариях.
- отчёт

## Как запустить

Из корня проекта (Python 3.10+):

```powershell
py run_lr3.py --policy both
```

Для просмотра сообщений и выбора режима назначения заказов:

```powershell
py run_lr3.py --policy both --assignment central --trace
```

Журналы появятся в `results_lr3/manual/`.

**Полная серия экспериментов:**

```powershell
py experiments_lr3.py
```

**Графики** (требуется `matplotlib`):

```powershell
py -m pip install -r requirements.txt
py plots_lr3.py
```

**Тесты:**

```powershell
py -m unittest discover -s tests -v
```

В экспериментальной серии алгоритм назначения заказов фиксирован (`central`); меняется **только правило выдачи места на зарядной станции**. Результаты воспроизводимы по `seed` и сохранены в `results_lr3/runs.csv` и `results_lr3/summary.csv`.

## Ограничения модели

Среднее время ожидания считается по заявкам, получившим разрешение на зарядку. Оставшиеся в очередях заявки отдельно учитываются в `pending_charge_requests` и `pending_max_wait`. Аварийное обслуживание робота длится 15 тиков, восстанавливает полный заряд без использования станции; незавершённый заказ возвращается диспетчеру. Это одинаковое для обоих режимов допущение модели.
